# 運営アカウント整備 & メール認証セットアップ手順

> ドメイン取得後にやること一式。**順序に意味があります**（後回しにすると二度手間になる部分があるため）。
> 対象: 運営共用アカウントの整備 / 認証メールの到達性改善 / 各サービスの権限移行 / （任意）独自ドメイン化

## 0. なぜこの順番か

```
① 運営共用アカウントを作る   ← 最初にやる。後からだと全サービスで作り直しになる
        ↓
② admin@ドメイン を用意（Cloudflare Email Routing・無料）
        ↓
③ Resend でドメイン認証 → DNSレコード登録
        ↓
④ Supabase の SMTP・テンプレート・レート制限
        ↓
⑤ 各サービスの権限を共用アカウントへ移行
        ↓
⑥（任意）Vercel を独自ドメインに
```

**①を飛ばして③④から始めると、後で全部作り直しになります。** Resend や各サービスを個人アカウントで登録してしまうと、引き継ぎのたびに移管作業が発生するためです。

---

## 1. 運営共用アカウントを作る

現状すべて個人アカウントになっているものを、**引き継ぎ可能な共用アカウント**に寄せます。

### 1-1. 共用メールアドレスを決める

| 方式 | 費用 | 長所 | 短所 |
|---|---|---|---|
| **共用Gmail**（推奨・まずはこれ） | 無料 | すぐ作れる。ドメインに依存しないので、万一ドメインが失効しても各サービスにログインできる | 共有アカウントなので2FAの管理に注意が必要 |
| Google Workspace | 約¥1,000/人/月 | 管理者が他ユーザーを作成・リセットできる。引き継ぎが正式に行える | 費用と設定の手間 |

**まずは共用Gmail（例: `kyudaiguild.ops@gmail.com`）を1つ作り、これを各サービスの登録アドレスにします。**

> ⚠️ **2FAの扱いに注意**: 共用アカウントの2段階認証を「個人のスマホのSMS」にすると、その人が引退した瞬間に誰もログインできなくなります。
> **認証アプリのシークレットをパスワードマネージャ（Bitwarden 等）で共有**し、復旧用の連絡先も複数人分登録してください。

### 1-2. `admin@ドメイン` を用意する（Cloudflare Email Routing・無料）

対外的な窓口として、独自ドメインのアドレスも用意します。

1. Cloudflare ダッシュボード → 対象ドメイン → **Email** → **Email Routing** を有効化
2. 「Destination addresses」に **1-1で作った共用Gmail** を登録し、届いた確認メールで承認
3. 「Routing rules」で `admin@ドメイン` → 共用Gmail の転送を作成
4. 案内される **MXレコード等は Cloudflare が自動で追加**します（DNSがCloudflareなので自動）

> **Email Routing は受信（転送）専用で、送信はできません。** サービスの登録先アドレスとしては
> **共用Gmail のほう**を使い、`admin@ドメイン` は名刺・問い合わせ窓口として使うのがおすすめです。

## 2. Resend で認証メールを送れるようにする

### 2-1. アカウント作成とドメイン認証

1. https://resend.com に **共用Gmail** でサインアップ
2. **Domains → Add Domain**
3. **サブドメインを指定する**（例: `send.ドメイン` や `mail.ドメイン`）
   > ルートドメインで送るより、サブドメインで送るほうが**ルートドメインの評判を守れます**。
   > また、1-2 の Email Routing がルートに MX を張るため、**競合を避ける意味でもサブドメイン推奨**です。
4. Resend が **SPF / DKIM 用のDNSレコード**を表示します

### 2-2. DNSレコードを登録（Cloudflare）

Cloudflare → 対象ドメイン → **DNS → Records** で、Resend が示したレコードをそのまま追加します。

- レコードは **Proxy status を「DNS only」（グレーの雲）** にしてください。オレンジの雲（Proxied）にすると認証が通りません
- 追加後、Resend の画面で **Verify** を押して緑になるのを確認

さらに **DMARC** を手動で追加します（Microsoft は送信者認証を厳しく見るため必須級）:

| Type | Name | Content |
|---|---|---|
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:admin@ドメイン` |

`p=none` は「拒否せず様子を見る」設定です。しばらく運用してレポートに問題がなければ `p=quarantine` に上げられます。

### 2-3. APIキーを発行

Resend → **API Keys → Create API Key**（権限は Sending access で十分）。
表示は一度きりなので、パスワードマネージャに保存してください。

## 3. Supabase の設定

### 3-1. カスタムSMTPを有効化

Supabase ダッシュボード → **Authentication → SMTP Settings**（`/auth/smtp`）

| 項目 | 値 |
|---|---|
| Enable Custom SMTP | ON |
| Sender email | `no-reply@send.ドメイン`（認証したドメインのアドレス） |
| Sender name | `九大ギルド` |
| Host | `smtp.resend.com` |
| Port | `465`（SSL/TLS）※ `587` でも可 |
| Username | `resend` |
| Password | 2-3 で発行したAPIキー |

### 3-2. 【重要】レート制限を上げる

**カスタムSMTPを保存すると、既定では「1時間あたり30通」に制限されます。** そのままだと新歓シーズン等で詰まります。

**Authentication → Rate Limits**（`/auth/rate-limits`）で、送信上限を実態に合わせて引き上げてください。

### 3-3. メールテンプレートを日本語にする

**Authentication → Email Templates** で、少なくとも **Confirm signup**（登録確認）を日本語に書き換えます。
既定の英語テンプレートのままだと、内容的にも迷惑メール判定的にも不利です。

- **件名**: `【九大ギルド】メールアドレスの確認`
- **本文**: `docs/email-templates/confirm-signup.html` の中身をそのまま貼り付け

サイトと同じ配色のHTMLメールになっています。画像とWebフォントを使っていないため、
表示崩れが起きにくく、迷惑メール判定でも不利になりません。

> リンクの有効期限は文面で「24時間」と書いています。
> **Authentication → Providers → Email** の有効期限設定を変更した場合は、文面も合わせて直してください。

### 3-4. Site URL / Redirect URLs の確認

**Authentication → URL Configuration** で、`Site URL` と `Redirect URLs` が現在のデプロイURLと一致しているか確認します。ここがズレていると確認メールのリンクが機能しません。

### 3-5. 【重要】新規ドメインは最初どこにも届かない

**設定が完璧でも、取得直後のドメインからのメールは迷惑メール送りになります。**
送信元としての実績（レピュテーション）がゼロのためで、設定をいじっても解決しません。

2026年8月の実測:

| 宛先 | 結果 |
|---|---|
| mail-tester（診断ツール） | **9.6/10**（SPF・DKIM・DMARC すべて通過、ブラックリスト無し） |
| Gmail | 届いたが**迷惑メールフォルダ** |
| `@s.kyushu-u.ac.jp` | **痕跡なく消失**（受信箱にも迷惑メールにも無い。Resendは delivered 表示） |

九大は Microsoft 365 で、Gmail より厳格です。スパム判定は検疫、フィッシング判定は
利用者に見せず削除する設定が一般的なため、「delivered なのにどこにも無い」状態になります。

**対処（効果の大きい順）**

1. **大学に許可リスト登録を依頼する ← 決定打**
   情報統括本部（情報共有基盤事業室）へ、送信ドメイン・送信日時・診断スコアを添えて問い合わせる。
   併せて**メッセージトレース**で実際の処理結果を確認してもらう
2. 受信できた人に「迷惑メールではない」を押してもらう
3. 少量を継続的に送って実績を作る（数日〜2週間。ただし組織フィルタには効きにくい）

**到達性が改善するまでの回避策**: 運営が Supabase に直接アカウントを作る
（手順は `docs/test-accounts.md`）。これでテストや小規模運用は止まりません。

> **構造的な論点**: 大学のフィルタは自分たちで制御できないのに、そこを通ることがサービスの
> 入口の条件になっています。**「Microsoftでログイン」（Entra ID OAuth）に切り替えれば
> 確認メール自体が不要**になり、この問題は根本から消えます。在籍確認としても確実です。
> テナント管理者の承認が必要なので、上記1の問い合わせと**同時に相談する**のが効率的です。

### 3-6. 送信テスト

アプリの登録フォームは九大ドメイン限定のため、**アプリを通さずにテストする**方法を使います。

- **Supabase ダッシュボード → Authentication → Users → Invite user**
  任意のアドレスへ、本番と同じ経路（Supabase → Resend → 受信側）で送信できます
- **mail-tester.com** の使い捨てアドレス宛に送ると、SPF/DKIM/DMARC の検証結果と
  スパム度の診断レポート（10点満点）が得られます

> `delivered` は「受信サーバーが受け取った」という意味で、**受信箱に入ったことは保証しません**。
> 受け取った後に検疫・削除されることがあるため、実際の受信箱で確認してください。

## 4. 各サービスの権限を共用アカウントへ移行

**全サービスで「共用アカウントを管理者として追加 → 個人アカウントは残す（すぐ消さない）」**の順で進めます。いきなり個人を外すと、締め出される事故が起きます。

| サービス | 操作 | 状態 |
|---|---|---|
| **Cloudflare** | Manage Account → Members → 共用Gmailを **Super Administrator** で招待 | ☐ |
| **Supabase** | Organization → Team → 共用Gmailを **Owner** で招待 | ☐ |
| **Vercel** | Settings → Members（Hobbyは個人アカウントのみのため、必要なら共用アカウントで新チーム作成 or プロジェクト移管） | ☐ |
| **GitHub** | リポジトリ（`sorairo-dev`）の Settings → Collaborators、または Organization 化して共用アカウントをOwnerに | ☐ |
| **LINE Developers** | プロバイダー / 各チャネルの権限管理で共用アカウント（ビジネスID）を **Admin** で招待 | ☐ |
| **LINE公式アカウント** | OA Manager → 権限管理 → 管理者として追加 | ☐ |
| **Resend** | Settings → Team（無料枠は人数制限あり。共用Gmailで作っていれば作業不要） | ☐ |
| **ドメイン** | Cloudflare アカウントを共用化すれば同時に移行完了 | ☐ |

> **Vercel の注意**: Hobby プランはチーム機能が使えません。共用アカウントで管理したい場合は、
> 共用アカウント側にプロジェクトを移す（Transfer）か、Pro プランでチームを作る必要があります。
> 当面は「個人アカウントのままだが、資格情報をパスワードマネージャで共有」でも実務上は回ります。

移行が完了し、**共用アカウントだけで全操作ができることを確認してから**、個人アカウントの権限を外してください。

## 5. （任意）Vercel を独自ドメインにする

優先度は低いですが、**やるなら早いほうが手戻りが少ない**です（URL変更に伴う設定更新が複数箇所あるため）。

### 手順
1. Vercel → プロジェクト → **Settings → Domains** → 独自ドメインを追加
2. Cloudflare の DNS に、Vercel が指示する **CNAME / A レコード**を追加（**DNS only** にする）
3. どのブランチに割り当てるか確認（既定では本番デプロイに紐づきます）

### 【重要】URL変更時に必ず更新が必要な箇所

ここを忘れると、LINEログインとメール認証が同時に壊れます。

| 場所 | 更新内容 |
|---|---|
| Vercel 環境変数 `NEXT_PUBLIC_SITE_URL` | 新しいURLに変更 → **Redeploy** |
| LINEログインチャネル → コールバックURL | `https://新URL/api/line/callback` を追加 |
| LINE Messaging API → Webhook URL | `https://新URL/api/line/webhook` に変更 |
| Supabase → URL Configuration | Site URL と Redirect URLs を更新 |
| Resend の DMARC `rua` | 変更不要（メールアドレスなので） |

移行直後は**旧URLの設定も残しておく**と、切り替え失敗時に戻せます。

- ☐ 新規登録の確認メールが**受信トレイ**に届く（迷惑メールではない）
- ☐ Resend のダッシュボードで `delivered` になっている
- ☐ Supabase のレート制限を引き上げた
- ☐ メールテンプレートが日本語になっている
- ☐ 共用アカウントだけで全サービスを操作できる
- ☐ パスワードマネージャに全資格情報と2FAシークレットが入っている
- ☐ ドメインの自動更新がON、支払い方法が有効
