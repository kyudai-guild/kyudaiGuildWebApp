# LINE連携 計画書

> **状態**: 計画のみ（実装未着手）。外部サービスのためアカウント作成・API取得は運営（人間）の作業が多い。
> この文書は「全体像の把握 → 運営側の準備 → 実装」の順で読めるようにまとめている。

## 1. やりたいこと（決定済み）

初期設定（①）でユーザーが選んだ **利用目的・興味分野** にマッチするクエストが承認・掲示されたとき、
**九大ギルド公式LINEアカウントから本人に Flex Message でプッシュ通知**する。
（メッセージの見た目は `ギルドLINE通知デモ_単体.json` / `_カルーセル.json` で確認済み）

## 2. 全体像 — 登場する仕組み

| 要素 | 何者か | 費用 |
|---|---|---|
| LINE公式アカウント (LINE Official Account) | ユーザーが「友だち追加」する窓口 | 無料プランあり |
| Messaging API チャネル | 公式アカウントにプログラムからメッセージを送るためのAPI | 無料 |
| チャネルアクセストークン | APIを叩くための秘密鍵（サーバー側環境変数に保存） | - |
| Webhook | ユーザーが友だち追加/メッセージ送信した時にLINE→我々のサーバーへ通知が来る仕組み | - |

**送信数の上限（重要・料金に直結）**:
- コミュニケーションプラン（無料）: 月 **200通** まで
- ライトプラン: 月 5,000通（月額 5,500円）
- 通知は「マッチしたユーザー数 × クエスト数」で消費するので、当面は無料枠で足りるが、
  ユーザーが増えたら **カルーセルで1日1回のダイジェスト送信**にまとめる等の節約設計が必要。

## 3. 一番の設計課題: 「サイトのアカウント」と「LINEのユーザー」の紐付け

LINEにプッシュするには相手の `LINE userId` が必要。サイトの profiles と LINE userId を繋ぐ方法は2案:

### 案A: 連携コード方式（実装がシンプル・推奨）
1. サイトのプロフィール画面に「LINE通知を受け取る」ボタン → 6桁の連携コードを表示
2. ユーザーは公式LINEを友だち追加し、トークにそのコードを送信
3. Webhook がコードを受け取り、profiles に `line_user_id` を保存 → 紐付け完了

### 案B: LINEログイン（アカウントリンク機能）
- LINE公式の account link 機能。UXは良いが、LINEログインチャネルの追加設定と
  リンクトークンのやり取りが必要で実装量が多い。**フェーズ2では見送り、案Aで開始**を推奨。

## 4. 運営（あなた）がやること — この順で

1. **LINE公式アカウント作成**: https://entry.line.biz/ （九大ギルド名義。認証済みアカウント申請は任意）
2. **LINE Developers コンソール**: https://developers.line.biz/console/
   - プロバイダー作成 → 作成した公式アカウントに **Messaging API チャネルを有効化**
3. チャネル基本設定から取得してメモ:
   - **チャネルシークレット**（Webhook署名検証に使用）
   - **チャネルアクセストークン（長期）** を発行
4. **応答設定**: あいさつメッセージON / 応答メッセージOFF / Webhook ON
5. Vercel の環境変数に登録（実装フェーズで）:
   - `LINE_CHANNEL_SECRET`
   - `LINE_CHANNEL_ACCESS_TOKEN`
6. Webhook URL を設定（実装後）: `https://<本番ドメイン>/api/line/webhook`

## 5. 実装フェーズの内容（運営準備が済んだら着手）

### DB（migration v7 として作成予定）
```sql
alter table profiles add column line_user_id text unique;      -- 紐付け先
alter table profiles add column line_link_code text;           -- 連携コード（一時）
-- line_notify boolean は v5 で導入済み（通知のON/OFF）
```

### APIルート
| ルート | 役割 |
|---|---|
| `POST /api/line/webhook` | LINEからの受信。署名検証 → followイベント/連携コードの処理 |
| `POST /api/line/link` | ログインユーザーに連携コードを発行 |
| 通知トリガー | 管理者がクエストを承認した時（`/api/quests/[id]/review` 内）に、興味・目的がマッチする `line_notify=true` かつ `line_user_id` ありのユーザーへ push |

### マッチングロジック（v5 のマスタ構造をそのまま利用）
- クエストに `quest_type` とタグがある → interest_options のラベルと突合
- 将来的にはクエスト作成時に「対象分野」を interest_options から選ばせると精度が上がる
  （マスタをDB化してあるので、クエスト側にも同じ選択肢を使い回せる）

### 送信内容
- 単発: `ギルドLINE通知デモ_単体.json` の形（altText 付きで送信）
- 1日のマッチが複数件: カルーセル形（送信数節約のため日次ダイジェスト化を検討）

## 6. セキュリティ・運用の注意

- チャネルアクセストークンは**絶対にクライアントに出さない**（`NEXT_PUBLIC_` を付けない）
- Webhook は必ず**署名検証**（`x-line-signature` を channel secret で HMAC-SHA256 検証）してから処理
- 通知の文言にはメールアドレス等の個人情報を入れない（クエストタイトル・種別・報酬まで）
- 退会/ブロック時は push が 4xx で返る → `line_user_id` をクリアする処理を入れる
